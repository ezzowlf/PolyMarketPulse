## THIS ROUND (newest) — Root-caused and fixed the "TLS-blocked" conclusion; real live FRED/CoinGecko/GDELT confirmed reachable; 30-market re-test with genuinely live data

**Major finding, overturning multiple prior rounds' conclusion**: FRED/CoinGecko/GDELT were never permanently network-blocked in this sandbox. The real cause: this machine runs an antivirus product (local TLS-inspection proxy) that issues its own root CA certificate, already trusted by the OS/Node.js (via the standard `NODE_EXTRA_CA_CERTS` env var) but unknown to Python's `certifi` bundle — so every `httpx` call using plain certifi failed with `CERTIFICATE_VERIFY_FAILED`, which earlier rounds correctly observed but incorrectly generalized to "sandbox network is blocked." Diagnosed live: `google.com` succeeded (200) while `fred.stlouisfed.org`/`api.coingecko.com`/`api.gdeltproject.org`/`federalreserve.gov`/`news.un.org` all failed identically with the same cert error — confirming a single common root cause (a locally-injected, not-yet-trusted CA), not a general egress block.

**Fix implemented (commit `1860d46`)**: `security.py::get_ca_bundle()`/`get_ssl_context()` — generic, environment-variable-driven (starts from certifi, additionally trusts whatever `NODE_EXTRA_CA_CERTS`/`SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE` points to if present and readable, else unchanged certifi-only fallback). No vendor name or path hardcoded anywhere in application code — verified via grep. `verify=False` never used anywhere — verified via grep. Wired into every real outbound HTTP client (`providers/fred.py`, `providers/coingecko.py`, `news/gdelt.py`, `news/rss.py`, and the other provider clients for consistency). Added `scripts/smoke_test_providers.py`, a standalone script using the identical helper, for the project owner to run on their own machine outside this sandbox — prints a precise per-provider HTTP/TLS/parsing result, never claims LIVE without a real successful request.
